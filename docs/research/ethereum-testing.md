# How the Ethereum ecosystem tests clients

Research note, 2026-11-09. Spawned's first users are Ethereum clients (ethrex,
ethlambda); this note surveys what the ecosystem already runs, to place
Spawned's testing work ([systematic testing](systematic-testing.md), ranks 5,
5c, 20-22a) where it adds something.

## What it is

Ethereum has many independent client implementations of one specification, so
its testing centres on *conformance* (does each client follow the spec),
*interoperability* (do different clients agree on a shared network) and
*resilience* (does a mixed network survive faults). Tools work at the level of
whole client binaries and networks.

## How it works

### Hive

"Hive is a system for running integration tests against Ethereum clients." A
*simulator* program launches clients in Docker through a common interface and
reports results; the Ethereum Foundation runs a public instance checking
consensus compatibility, p2p spec compliance and user APIs, with results at
[hive.ethpandaops.io](https://hive.ethpandaops.io)
([overview](https://github.com/ethereum/hive/blob/master/docs/overview.md)).
Hive's `clients/` directory includes both `ethrex` and `ethlambda` (checked
2026-11-09).

### Kurtosis devnets (`ethereum-package`)

ethPandaOps' Kurtosis package "deploys a private, portable, and modular
Ethereum devnet" over Docker or Kubernetes, with any mix of execution and
consensus clients (ethrex is a supported execution client), plus optional
services: Assertoor test runs, transaction spammers and fuzzers, and
Disruptoor for partitions and traffic shaping
([ethereum-package](https://github.com/ethpandaops/ethereum-package)).
Ethlambda's lean-consensus devnets use a separate tool,
[lean-quickstart](https://github.com/lambdaclass/lean-quickstart).

### Attacknet (Trail of Bits with the EF)

Chaos testing on top of Kurtosis devnets: "Attacknet uses Chaos Mesh to inject
faults into a devnet environment generated by Kurtosis." Faults include clock
skew, network latency and partitions, gossip packet drop or corruption, forced
client crashes, and disk I/O faults; after each fault it runs health checks on
every node and saves logs when one fails. Trail of Bits built it "in
collaboration with the Ethereum Foundation" and it was used to test the Dencun
hard fork ([Trail of Bits](https://blog.trailofbits.com/2024/03/18/releasing-the-attacknet-a-new-tool-for-finding-bugs-in-blockchain-nodes-using-chaos-testing/);
[ethPandaOps](https://ethpandaops.io/posts/attacknet-introduction);
[crytic/attacknet](https://github.com/crytic/attacknet)). Faults are real, not
simulated, so runs are not deterministic.

### ethshadow (Shadow)

[Shadow](https://shadow.github.io/) runs unmodified Linux binaries, intercepts
their system calls and routes traffic through a simulated network in a
discrete-event simulation; "Shadow simulations are deterministic, so bugs are
identically reproduced by re-running the simulation", and one machine can
simulate thousands of nodes. [ethshadow](https://ethereum.github.io/ethshadow)
configures Ethereum networks on Shadow with the real client binaries. As of its
README, Geth, Lighthouse and Prysm work out of the box, Reth works with
modifications, Besu, Nethermind and Teku do not work, and others are untested;
new client types need an adapter in `ethshadow`'s `lib/src/clients`
([repository](https://github.com/ethereum/ethshadow)).

### Antithesis

Antithesis runs containers inside a deterministic hypervisor and injects
faults; a failure can be replayed exactly
([product](https://antithesis.com/resources/deterministic_simulation_testing/)).
Its own case study says the EF "began working with Antithesis to test the Merge
codebase" about a year before the Merge, ran the whole network inside it and
found dozens of bugs ([case study](https://antithesis.com/case_studies/ethereum_merge)).

Sources outside the vendor are thin but exist:

- The EF's *Quest for the best tests: a retrospective on #TestingTheMerge*
  (Parithosh Jayanthi, Devcon VI, 2022) describes Antithesis as offering "a
  deterministic hypervisor which allows us to perform network splits, packet
  loss while fuzzing clients" ([talk](https://archive.devcon.org/devcon-6/quest-for-the-best-tests-a-retrospective-on-testingthemerge)).
  We saw the slide text only through a search index (the slide PDF link
  returned 404 when checked), so treat the quotation as unverified.
- ethPandaOps (the EF's DevOps team) publishes
  [antithesis-runs](https://github.com/ethpandaops/antithesis-runs) (created
  2025), GitHub workflows that run Antithesis against the Kurtosis
  `ethereum-package`.

We found no EF primary source on Antithesis use for specific later upgrades
(Shapella, Dencun, Pectra); the vendor's claims about those are unverified.

### Fuzzing

- **Differential fuzzing of consensus clients:** Sigma Prime's
  [beacon-fuzz](https://github.com/sigp/beacon-fuzz), maintained for the EF,
  fed the same inputs to several beacon-chain implementations and compared
  results; it reported consensus bugs including an off-by-one in Prysm
  attestation processing. Its reports are from the 2019-2021 era.
- **EVM differential fuzzing:** [goevmlab](https://github.com/holiman/goevmlab)
  (a go-ethereum developer's lab) and
  [FuzzyVM](https://github.com/MariusVanDerWijden/FuzzyVM) generate state tests
  and compare EVM traces across clients.
- Devnets add transaction fuzzers (`tx_fuzz` in `ethereum-package`).

### Formal verification of the consensus specification

- **Runtime Verification:** an executable K model of the Beacon Chain state
  transition (2019, with EF collaborators) and Coq proofs of Gasper finality
  (accountable safety, plausible liveness) under dynamic validator sets
  ([K model](https://runtimeverification.com/blog/a-formal-model-in-k-of-the-beacon-chain-ethereum-2-0s-primary-proof-of-stake-blockchain);
  [Gasper](https://runtimeverification.com/blog/formally-verifying-finality-in-gasper-the-core-of-the-beacon-chain)).
- **ConsenSys, Dafny:** Cassez, Fuller and Asgaonkar verified absence of
  runtime errors and functional properties for a large part of the Phase 0
  Beacon Chain reference, finding and fixing spec issues (TACAS 2022)
  ([paper](https://arxiv.org/abs/2110.12909);
  [eth2.0-dafny](https://github.com/PegaSysEng/eth2.0-dafny)).
- **TLA+ / Apalache:** Konnov, Kukovec, Pani, Saltini and Tran model-checked
  accountable safety of the 3-slot-finality (3SF) protocol on small instances,
  cross-checked with Alloy and SMT
  ([arXiv 2501.07958](https://arxiv.org/abs/2501.07958)).

These verify the *protocol specification*, not client implementations or
their concurrency.

## Who uses it

All of the above are used by the Ethereum Foundation or its client teams, as
cited per tool. Specifically: Hive and Kurtosis devnets run continuously at
the EF (ethPandaOps); Attacknet was used for Dencun; ethshadow is an
`ethereum` organization project; Antithesis use for the Merge is documented by
the vendor and an EF talk (see caveats above).

## What it means for Spawned

What the ecosystem covers: spec conformance (Hive, reference tests),
cross-client interoperability (devnets), network-level faults (Attacknet,
Antithesis, ethshadow) and protocol-level proofs. What it does not cover:

1. **Inside one client.** All tools treat a client as a black box. None
   explores the orderings of messages *between a client's own actors*, which
   is where the client sweep found its bugs: racy shutdown, a duplicate
   connection's cleanup removing the live entry (#7435), deadlocked imports,
   wedged handlers ([client sweep](../../ROADMAP.md#client-sweep-production-pain)).
   Rank 20 (`explore`) and ranks 21-22 (crash tapes, record and replay) give
   ethrex and ethlambda deterministic, seed-reproducible tests at that level,
   in `cargo test`, without a cluster.
2. **Checking the runtime's own invariants in production.** Health checks ask
   "is the node still following the chain"; they do not say *which* internal
   contract broke. Rank 5c's monitors report, in a live node, a supervisor
   that published a stale generation, broke reverse shutdown or left a request
   unanswered ([PObserve for Spawned](systematic-testing.md#a-pobserve-for-spawned)).

How the hosts fit the ethlambda canary (rank 5):

- **Attacknet** is the shortest path to the "fault injection in the Ethlambda
  canary" release gate in [testing to add](../../ROADMAP.md#testing-to-add)
  for beacon-chain mode with ethrex, since both run under Kurtosis today:
  partitions, clock skew and crashes from outside, with Spawned's offline
  monitors (rank 5c, mode b) reading the traces each node writes. Lean-chain
  mode needs its devnet tooling first.
- **ethshadow** would make those runs deterministic and replayable, at the cost
  of an ethlambda (and ethrex) adapter and Shadow compatibility work; the
  ethshadow table shows several clients do not yet run there. Worth it once a
  canary failure needs exact reproduction.
- **Antithesis** offers the same with less integration work but is
  commercial and not reproducible locally.
