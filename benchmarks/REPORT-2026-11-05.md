# Initial Spawned performance baseline

Date: 2026-11-05. This is a local microbenchmark analysis, not a production
client benchmark or a comparison against Silver. Production library code was
not changed. See [methodology and reproduction](README.md).

## Environment and validation

- Apple M5 Max, 18 physical/logical CPUs, 128 GiB RAM, Darwin 25.6.0 / arm64.
- Rust 1.93.0, Cargo 1.98.0, optimized Cargo bench profile with default profile
  settings; no core affinity. CPU placement, power policy and other host load
  were not controlled. This shared development host showed substantial variance.
- Source revision `6596704` (full hash and executable/source hashes in metadata),
  based on Spawned main `1b78ca8`. The benchmark source was committed and clean
  before both campaigns. Existing runtime defaults were retained in the first.
- Five repetitions of nine cases across five implementations: 225 processes,
  5,750,000 measured requests, with request-ID and completion-count checks.
- Separate follow-up: three repetitions of three cases across five implementations,
  45 processes, with `TOKIO_WORKER_THREADS=1`. Driver worker count remains two.
- All 45 case/backend smoke combinations completed; the workspace suite,
  formatting and Clippy with warnings denied passed.

The report uses medians of per-process values. A median of run-level p99s is not
a pooled p99. CPU/RSS include setup, warmup, sample storage, analysis and teardown.
The first campaign began while a workspace validation run was finishing; that
can affect early samples and reinforces the need to repeat on a quiet machine.
There was no concurrent validation command during the follow-up campaign.

## Single sequential request producer

One actor, one producer, 20,000 measured requests, shared 64-byte payload.
Throughput includes caller waiting and benchmark-driver wakeups.

| Backend | Replies/s, median (min–max) | Handler-completion p99, µs | Observed-reply p99, µs | Process peak RSS, MB |
|---|---:|---:|---:|---:|
| async | 111,679 (80,687–117,219) | 17.8 | 26.9 | 8.7 |
| blocking | 136,648 (46,575–178,752) | 11.4 | 21.1 | 8.8 |
| dedicated | 100,524 (64,978–185,389) | 20.8 | 38.0 | 9.5 |
| threads | 129,295 (67,476–198,251) | 10.2 | 19.3 | 8.8 |
| tokio | 97,097 (92,852–121,530) | 16.5 | 23.9 | 8.7 |

Ranges overlap or vary widely. These results do not establish a universal backend
winner or a significant improvement over plain Tokio. The trivial handler's
elapsed time is much smaller than the queue/scheduling/reply path. Handler-start
measurement includes some framework work before entry; it cannot isolate channel,
allocation and scheduling costs. Use a profiler before attributing them.

## Many mostly idle actors

128 actors are initialized, but only four receive measured traffic from four
producers. Compare this case with `rpc_parallel`, which has four actors with the
same active traffic. This is an actor-retention experiment, not 128-way saturation.

| Backend | Replies/s, median (min–max) | Handler-completion p99, µs | Observed-reply p99, µs | Process peak RSS, MB |
|---|---:|---:|---:|---:|
| async | 227,457 (186,526–313,708) | 32.9 | 53.2 | 11.4 |
| blocking | 177,677 (155,825–222,233) | 33.5 | 51.7 | 14.1 |
| dedicated | 24,658 (19,144–25,687) | 251.7 | 336.9 | 81.4 |
| threads | 233,485 (184,239–268,491) | 25.6 | 42.1 | 13.9 |
| tokio | 233,760 (127,752–291,116) | 28.9 | 43.7 | 11.3 |

The dedicated task backend is the clear configuration concern in this case.
Source inspection explains a plausible mechanism: each `Backend::Thread` invokes
`spawned_rt::threads::block_on`, which constructs `Runtime::new()`. Each actor
therefore has its own default Tokio runtime, independently of the driver's two
workers. Synchronous thread actors do not construct those per-actor runtimes.

The follow-up changes the default runtime worker count via environment only:

| Dedicated backend, 128 actors | Replies/s median | Completion p99, µs | Process peak RSS, MB |
|---|---:|---:|---:|
| Default runtime workers (5 runs) | 24,658 | 251.7 | 81.4 |
| One worker per runtime (3 runs) | 180,095 | 29.8 | 20.5 |

This supports investigating runtime proliferation and worker configuration before
replacing Tokio. It does not prove which part is thread scheduling, memory,
startup effects or locality. The campaigns differ in repetition count and ran at
different times. A current-thread runtime or a shared runtime is a candidate
experiment, not an implemented optimization. Test nested spawning, timers, I/O,
blocking callbacks, cancellation and shutdown before changing backend defaults.

## Burst traffic

Four producers enqueue 50,000 requests to one actor, with separate reply collectors.
There is no arrival rate constraint. This exercises finite burst buffering and drain
behavior, rather than an indefinitely sustainable offered load.

| Backend | Replies/s, median (min–max) | Handler-completion p99, µs | Observed-reply p99, µs | Process peak RSS, MB |
|---|---:|---:|---:|---:|
| async | 3,345,852 (2,413,074–3,407,968) | 3,265.8 | 7,544.1 | 19.0 |
| blocking | 2,728,904 (2,527,785–3,256,339) | 2,250.5 | 7,366.6 | 18.7 |
| dedicated | 3,194,812 (2,767,221–3,874,004) | 2,611.2 | 6,366.8 | 19.6 |
| threads | 1,735,895 (1,293,088–2,359,497) | 20,740.5 | 20,743.3 | 40.3 |
| tokio | 3,704,161 (3,007,293–3,793,351) | 419.0 | 4,785.6 | 16.2 |

Synchronous thread actors have appreciably worse burst tails in this run despite
competitive sequential-request results. That illustrates why a thread-per-actor
ping-pong result alone is insufficient for choosing a backend. Queue/transport and
driver collection need profiling before assigning a cause. The plain Tokio loop
also has different dispatch machinery; its behavior is a useful baseline, not
proof that every actor abstraction is unnecessary.

## Scheduled CPU load and overload

A 64-byte scan plus 20,000 dependent integer iterations is performed by one actor.
Four producers schedule 10,000 arrivals in total at 20k/s or 200k/s. They do not
wait for previous replies, but OS sleep resolution and enqueue lag affect delivery.

| Backend | 20k/s completion p99, ms | 200k/s completion p99, ms | 200k/s completed replies/s |
|---|---:|---:|---:|
| async | 1.16 | 360.1 | 24,208 |
| blocking | 2.22 | 339.2 | 25,448 |
| dedicated | 2.43 | 363.2 | 24,030 |
| threads | 2.47 | 335.9 | 25,680 |
| tokio | 0.74 | 345.7 | 25,059 |

All implementations finish the finite high-load burst, but they drain at roughly
24–26k replies/s against an offered 200k/s. Completion p99 grows to roughly
0.34–0.36 seconds. In the raw data, queue wait dominates that tail. This supports
explicit overload/admission policies: a different scheduler cannot eliminate a
persistent arrival/service-rate mismatch. Finite completion is not evidence that
unbounded buffering is safe. Long-duration memory growth was not measured here.

At 20k/s, producers largely sustain the scheduled rate, while tail latency still
shows jitter. Enqueue-lag samples are retained to expose generator lateness;
these experiments do not reproduce real network arrivals or mixed async I/O.

## Allocation and measurement observations

In the allocation-enabled sequential RPC case, the median measured counts are:

| Backend | Alloc/realloc calls per measured request |
|---|---:|
| async | 3.000 |
| blocking | 3.000 |
| dedicated | 3.000 |
| threads | 5.032 |
| tokio | 1.000 |

These are whole measurement-window counts, including driver activity, not an
isolated framework allocation profile. Spawned's task path has about two more
calls/request than this plain Tokio baseline, consistent with its boxed envelope
and boxed handler future. Confirm attribution with allocation profiling before
optimizing ownership or dispatch. Thread-channel counts have additional costs
that this experiment does not isolate.

Timing-off and counting-enabled runs are retained in the data. Their throughput
ranges are broad, and some instrumented runs happen to be faster. Do not infer a
negative instrumentation cost from that ordering. Re-run paired controlled
experiments before estimating overhead. The allocator wrapper always checks a
flag; timing-off still captures completion timestamps and keeps the same payload
layout. No production exporter or zero-instrumentation build was tested.

## What to do next

1. Reproduce on a quiet Linux target with explicit CPU/NUMA placement and equal
   CPU budgets. Include 128 active actors separately from idle retention.
2. Profile the dedicated backend's per-actor runtimes; prototype current-thread
   or configurable runtime construction and compare against the retained baseline.
3. Profile burst queueing and allocation sources. Add send-only and real async I/O
   cases, and integrate one reproducible Ethrex or Ethlambda workload.
4. Add optional framework queue/lifecycle metrics with measured off/on/sampled
   cost, using these baseline workloads as checks.
5. Evaluate bounded admission when workload evidence requires it; test wait/reject,
   shutdown and cyclic-send behavior without silently changing request delivery.

## A Silver-inspired option

No pinned-core, spinning or preallocated-mailbox backend was tested. The current
native-thread mode is not equivalent to Silver's tile/spine transport.

A separate experimental backend could combine a dedicated core, bounded
preallocated addressed mailbox and selectable park/spin/hybrid waiting policy.
Keep protocol and reply semantics; define full-mailbox outcomes explicitly.
Preallocating queue slots alone does not remove boxed-envelope or handler-future
allocations. Heterogeneous ordinary Rust messages would need an explicit storage
strategy (for example pooling with a fallback); an allocation-free claim would
require stronger constraints and separate validation.
Do not introduce broadcast, Copy-only messages or silent overwrites as defaults.
Measure equal CPU budgets, idle CPU/power, tail latency, memory and shutdown
latency. The current baseline supports making that an experiment, not deciding
in advance that it will outperform existing backends. See the
[Silver/flux research](../docs/research/silver-flux.md).
